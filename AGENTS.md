# Redação HG

## 0. Doutrina editorial, a raiz da escrita

Esta secção está acima de todas as outras na parte da escrita. Toda a peça produzida pela Redação HG, por qualquer agente de texto, ChatGPT, Claude ou outro, e por qualquer prompt ou skill, obedece primeiro a esta doutrina. A doutrina completa está no ficheiro `ESTILO-EDITORIAL-HG.md`, na raiz do projecto, e deve ser carregada e respeitada por todos os agentes de escrita, de Discover, de SEO, de redes sociais e de revisão.

**Estrela polar.** Deixamos de gritar o que o adepto sente, passamos a explicar, melhor do que ninguém, aquilo que o adepto quer perceber. Da indignação para a autoridade.

**Porquê.** O site perdeu o Google Discover em outubro de 2025 e, com ele, a maior parte do tráfego e da receita. A causa provável foi o conteúdo de indignação sobre arbitragem e rivais, que a Google passou a penalizar. Esta doutrina existe para reconquistar o Discover e proteger o site.

**Fosso do projecto.** O Hugo Gil é ex-árbitro, ex-jogador e comentador. A arbitragem é tratada como análise de especialista, com as leis do jogo e o protocolo do VAR, e não como queixa. A voz de adepto mantém-se, mas sempre fundamentada.

**Sete regras de ouro, resumo.**

1. Ângulo próprio obrigatório, nada de resumos sem valor acrescentado.
2. Arbitragem com autoridade, com o selo de ex-árbitro.
3. Título honesto, apelativo mas nunca enganador, entrega o que promete.
4. Facto verificado, nenhuma afirmação forte sem fonte sólida.
5. Imagem própria, 1200 píxeis, 16 por 9, sem logótipo nem texto por cima.
6. Publicidade equilibrada, a publicidade não pode exceder o conteúdo.
7. Assinatura e data visíveis, com credenciais do autor.

**Método dos três níveis, obrigatório em cada peça.** Facto, o que aconteceu. Análise, o que só nós explicamos. Autoridade, quem o diz e porque é credível. Uma peça só com facto é um resumo, e resumos já não trazem tráfego.

O Agente Revisor rejeita qualquer peça que falhe a checklist de aprovação da doutrina. O Agente Discover e o Agente SEO aplicam as regras de título honesto e de imagem. Ver `ESTILO-EDITORIAL-HG.md` para os detalhes, os exemplos do que se pode e não se pode, e as regras por tipo de conteúdo.

## 1. Identidade do projecto

**Nome do projecto:** Redação HG

**Objectivo:** construir uma redação editorial assistida por agentes para o site HugoGil.pt.

A Redação HG deve funcionar inicialmente no computador local, depois numa rede interna e, no futuro, numa VPS ou aplicação desktop.

A aplicação deve permitir ao utilizador controlar todas as fases do processo editorial, desde a recolha de notícias até à criação de rascunhos no WordPress e preparação de conteúdos para redes sociais.

A Redação HG não é uma máquina automática de publicação. É uma redação assistida por IA com mão humana obrigatória.

---

## 2. Princípio principal

Nada pode ser publicado, enviado, apagado, alterado ou distribuído sem aprovação humana explícita.

Sempre que existir dúvida, risco editorial, risco legal, conflito entre fontes ou possibilidade de erro factual, o sistema deve parar e pedir validação humana.

---

## 3. Papel do Codex

O Codex é a ferramenta usada para construir, organizar, corrigir, testar e manter a aplicação.

O Codex deve trabalhar como:

- Arquitecto técnico
- Programador sénior
- Responsável de produto
- Consultor editorial
- Revisor de segurança
- Organizador de agentes e skills

O Codex não deve ser o motor permanente da redação. A aplicação criada é que deve executar os fluxos editoriais.

---

## 4. Papel do ChatGPT

A Redação HG deve permitir usar a OpenAI API, ChatGPT, como agente principal de escrita editorial.

O ChatGPT deve ser usado para:

- Criar notícias originais com base em factos recolhidos
- Escrever textos em português europeu
- Criar títulos para Google Discover
- Criar títulos SEO
- Criar meta descrições
- Criar slugs
- Criar posts para Facebook
- Criar textos para WhatsApp
- Criar push notifications
- Criar versões alternativas de texto
- Comparar abordagens editoriais
- Rever clareza, contexto e risco de cópia
- Ajudar a separar notícia, opinião, análise e crítica

A aplicação deve permitir escolher o motor de texto:

- ChatGPT
- Codex
- Outro modelo futuro
- Comparação entre modelos

O utilizador deve conseguir gerar uma versão com ChatGPT, outra com Codex e comparar antes de aprovar.

## 5. Regra sobre limites de texto

Não existe limite rígido global de texto.

A Redação HG deve permitir textos curtos, médios ou longos, conforme a necessidade editorial.

O tamanho do texto deve ser definido por:

- Instrução directa do utilizador
- Tipo de conteúdo
- Importância do tema
- Profundidade necessária
- Objectivo editorial
- Plataforma de publicação

A aplicação deve sugerir tamanhos recomendados por formato, mas nunca deve bloquear um texto por ter mais ou menos palavras, salvo ordem explícita do utilizador.

Exemplos de formatos possíveis:

- Notícia curta
- Notícia desenvolvida
- Análise
- Opinião
- Crítica
- Resumo rápido
- Texto para Discover
- Texto para redes sociais
- Texto para push
- Texto para WhatsApp
- Texto longo de enquadramento
- Dossiê editorial

Quando o utilizador pedir um limite específico, esse limite deve ser respeitado. Quando o utilizador não pedir limite, o agente deve escolher o tamanho adequado ao contexto.

## 6. Idioma

Todos os textos devem ser escritos em português europeu.

Regras obrigatórias:

- Nunca usar português do Brasil
- Evitar expressões brasileiras
- Usar vocabulário natural em Portugal
- Escrever de forma humana, directa e editorial
- Evitar linguagem robótica
- Não usar anglicismos desnecessários
- Não usar o símbolo de travessão
- Não tentar substituir o travessão por outro símbolo para criar pausas artificiais
- Usar vírgulas quando for necessário marcar ritmo
- Escrever com clareza e força editorial

---

## 7. Estilo editorial base

A Redação HG deve produzir textos com:

- Clareza
- Contexto
- Força noticiosa
- Linguagem humana
- Títulos com impacto
- Precisão factual
- Boa leitura em mobile
- Potencial para Google Discover
- Potencial para redes sociais
- Separação clara entre facto e opinião

O tom pode variar entre:

- Informativo
- Forte
- Crítico
- Neutro
- Opinativo
- Editorial
- Irónico
- Analítico
- Desportivo
- Político

O tom deve ser escolhido pelo utilizador ou sugerido pelo sistema com base no tema.

---

## 8. Separação entre notícia e opinião

O sistema deve distinguir sempre:

- Notícia
- Opinião
- Análise
- Crítica
- Rumor
- Informação de mercado
- Comunicado
- Post para redes sociais
- Conteúdo humorístico
- Meme

Nunca transformar opinião em notícia. Nunca transformar rumor em facto. Nunca apresentar uma possibilidade como certeza. Nunca inventar declarações, números, lesões, negociações, contratos, fontes ou datas.

---

## 9. Fontes e direitos editoriais

O sistema deve recolher informação de fontes noticiosas, mas não deve copiar textos.

Regras obrigatórias:

- Nunca copiar o corpo de notícias de outros sites
- Nunca reescrever parágrafo a parágrafo
- Nunca usar frases características de outros meios
- Nunca usar imagens de outros sites como imagem destacada sem autorização
- Guardar sempre título, URL, fonte, data e hora
- Guardar pequenos excertos apenas quando forem necessários para contexto ou verificação
- Preferir extracção de factos a cópia de texto
- Cruzar fontes sempre que possível
- Manter o contexto original
- Indicar quando a informação vem de uma fonte específica
- Não distorcer o sentido da notícia original
- Não criar títulos enganadores
- Não criar falsas certezas
- Não omitir informação essencial que altere o contexto
- Não criar conteúdo com aparência de notícia quando só existe especulação

## 12. Agrupamento de notícias

O sistema deve agrupar notícias sobre o mesmo tema.

**Exemplo:**

- Fonte 1: Benfica atento a médio argentino
- Fonte 2: Encarnados seguem jogador do River Plate
- Fonte 3: Médio argentino associado ao Benfica

O sistema deve perceber que pode tratar-se do mesmo tema e criar um grupo editorial.

Cada grupo deve ter:

- Tema principal
- Fontes associadas
- Grau de confiança
- Contradições entre fontes
- Factos confirmados
- Factos não confirmados
- Sugestão de abordagem editorial
- Sugestão de prioridade
- Estado editorial
- Botões de acção

## 27. Stack técnica recomendada

Construir a aplicação com foco em portabilidade entre computador local, rede interna e VPS.

- Next.js para a interface
- React para componentes
- shadcn para UI
- Node.js com NestJS para backend, salvo decisão técnica diferente
- PostgreSQL para base de dados
- Redis com BullMQ para filas e tarefas agendadas
- Docker e Docker Compose
- Prisma ou ORM equivalente
- REST API para WordPress
- OpenAI API para ChatGPT
- Anthropic API para Codex, quando aplicável
- Google Drive API para imagens
- React Flow ou solução equivalente para interface visual futura
- Playwright para testes
- Nginx ou Caddy para VPS
- Backups automáticos para produção

O projecto deve poder correr em:

- Mac
- Windows
- Rede interna
- VPS
- Futuramente, aplicação desktop com Tauri ou Electron, se fizer sentido
